# Domain Model

## Objective

Represent the entities, behaviors, and invariants of the SetupShop domain.

## Current Scope

This diagram represents system elements to improve visualization and modeling.

```mermaid
classDiagram
    direction TB

    class Product {
        <<aggregateroot>>
        -Long id
        -String name
        -String description
        -BigDecimal price
        -boolean active
        +updateDetails()
        +deactivate()
    }
    note for Product "Name and price are required;
        Description is optional;
        Price must be non-negative and have no more than two decimal places."

    class Customer {
        <<aggregateroot>>
        -Long id
        -String name
        -String email
        -String phone
        -boolean active
        +updateDetails()
        +deactivate()
    }
    note for Customer "Name, email, and phone number are required;
        Email is stored in lowercase;
        Phone number must contain exactly 11 digits without formatting."

    class Account {
        <<aggregateroot>>
        -Long id
        -String email
        -String passwordHash
        -Long customerId
        -AccountRole role
        -Instant createdAt
        -Instant updatedAt
    }
    note for Account "Login email is required, normalized to lowercase, and unique;
        A non-blank password hash and a role are required;
        CUSTOMER accounts require a Customer ID;
        A supplied Customer ID must be positive and reference an existing Customer;
        Each Customer can have at most one Account;
        Timestamps are managed by the database."

    class AccountRole {
        <<enumeration>>
        CUSTOMER
        ADMIN
    }

    class Order {
        <<aggregateroot>>
        -Long id
        -Long customerId
        -List~OrderItem~ orderItems
        -OrderStatus status
        -Instant createdAt
        -BigDecimal total
    }
    note for Order "Customer ID must be valid;
    The order must contain at least one non-null item;
    Initial status is CREATED;
    Total is calculated from item subtotals when the order is created and remains recorded;
    CreatedAt is generated by the database."

    class OrderItem {
        <<valueobject>>
        -Long productId
        -int quantity
        -BigDecimal unitPrice
        +subtotal()
    }
    note for OrderItem "Product ID must be valid;
    Quantity must be greater than zero;
    Unit price must be non-negative and have at most two decimal places;
    Unit price is captured when the order is placed;
    Subtotal is unit price multiplied by quantity."
        
    Customer "1" --> "0..*" Order: places (customerId)
    Customer "0..1" <-- "0..1" Account: references (customerId)
    Account --> AccountRole: role
    Order "1" *-- "1..*" OrderItem: contains
    Product "1" <-- "0..*" OrderItem: references (productId)
``` 

Account domain and persistence are implemented. Registration, password hashing,
authentication, and authorization remain planned. The optional Customer link in
the diagram reflects the current mapping; `CUSTOMER` accounts always require
that link. Administrator creation and Customer linkage rules remain open.

The adopted hashing design uses Argon2id with automatic salt and a secret
pepper. Hashing and verification will happen outside Account. The pepper is
kept outside the database and is not an Account field. The encoding format and
secret lifecycle remain to be defined; see the
[password hashing decision](../decisions.md#password-hashing-with-argon2id-and-pepper-planned).
